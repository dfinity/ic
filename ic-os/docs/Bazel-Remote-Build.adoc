= Building IC-OS images with Bazel caching and remote execution

:toc:

== Problem

IC-OS images were built outside Bazel's usual guarantees:

* *No sandbox, no remote execution.* `bazel/conf/.bazelrc.build` had
  `--strategy_regexp=ic-os[:/].*=local`, which forced *every* action whose
  description mentions an `ic-os` package to run directly on the host. That
  covered the `podman` container builds and also the ext4/vfat/disk/LVM image
  steps, verity signing and launch measurements. (Tests were not affected:
  Bazel never applies `--strategy_regexp` to the `TestRunner` mnemonic.)
* *No cache.* Most partition and image targets were tagged `no-cache`, added in
  #3256 to save disk-cache space (24G vs 6.9G per build) on the grounds that
  "the images are rebuilt on almost every change anyway". The result is that
  every PR that needs an image (any system test) rebuilds the boot, root, ESP,
  LVM, disk and upgrade images from scratch, even when their inputs are
  bit-for-bit unchanged.
* *Privileged CI.* Because the `podman` steps run on the host, the CI
  containers run `--privileged` with a tmpfs at `/tmp/containers`.
* *Every PR builds all of IC-OS.* The `build-ic` job of `ci-main.yml` always
  runs `ci/container/build-ic.sh -i` with `--config=local`. This is
  deliberate: it is the uncached half of the build-determinism comparison.

|no privileges: they only read and write regular files. They do use host tools

the CI image, which `rbe.bazelrc` already requires

Most IC binaries are injected *after* the container build, by `ext4_image`
(`extra_files`). So `rootfs-tree.tar` depends on the pinned base image, the
files in `ic-os/components`, and the few binaries listed as component files.
On GuestOS that is `//rs/ic_os/open_rootfs`, which goes into the initramfs
(`ic-os/components/guestos.bzl`). The privileged step is therefore invalidated
by IC-OS component changes and by Rust changes in `open_rootfs`'s dependency
tree (e.g. `rs/nns/governance/api`, `rs/ic_os/config`), but not by most other
Rust changes, such as the replica. Builds without
`--config=stamped` use the constant version
`0000000000000000000000000000000000000000` (see `bazel/workspace_status.sh`),
so unchanged inputs produce unchanged action keys across PRs. CI's
`build-determinism` job already checks that these outputs are reproducible.

== Cache everything, run unprivileged steps anywhere

* Each sysimage action gets a mnemonic (`IcosExt4Image`, `IcosDiskImage`, ...).
  Only `IcosContainerBaseImage` and `IcosContainerBuild` (see
  `ICOS_CONTAINER_MNEMONICS` in `toolchains/sysimage/toolchain.bzl`) are forced
  `local`, via `--strategy=<mnemonic>=local`. Everything else follows the normal
  spawn strategy: sandboxed locally, `remote` on RBE. `IcosContainerBuild`
  outputs stay cached; `IcosContainerBaseImage` keeps `no-remote-cache`
  because its `apt install` isn't reproducible.
* The `podman` wrapper (`proc_wrapper.sh`, which needs `podman unshare` or
  `sudo` to clean up) is now used only by the container actions. All other
  actions use `tmpdir_wrapper.sh`, which manages a private `TMPDIR` in the
  action's working directory and sets `FAKEROOTDONTTRYCHOWN` (see the notes
  below).
* `no-cache` is removed from all image targets, including the uncompressed
  intermediates (`disk-img.tar`, `disk-img-for-tests.tar`, `update-img*.tar`)
  and the unsigned root partition. Excluding those from the cache doesn't
  save much: Bazel needs an action's input digests to compute its cache key,
  so an uncached intermediate gets rebuilt on every run before its compressed
  or signed successor can be fetched. Those are the most expensive actions,
  and `disk-img-for-tests.tar` is also used directly by
  `//rs/ic_os/os_tools/guest_vm_runner` tests. On RBE, outputs land in the
  CAS anyway. The `local-base-*` envs keep their `no-cache` tag, but
  `icos_build` only passes it to the top-level filegroup and the conformance
  test. Their partitions and images are cacheable too, which is harmless:
  their keys include the digest of the non-reproducible `base_image.tar`, so
  they never hit.
* `fakeroot` is listed explicitly in `ci/container/files/packages.common`.
  It is already in the image as a `Recommends` of `dpkg-dev` (via
  `build-essential`), but the image actions now rely on it on remote workers.
* The two remaining genrules that need the host (the `podman` bootloader tree
  and the `fuse2fs` bootfs extraction) are tagged
  `no-sandbox` + `no-remote-exec`. Their outputs are still cached.
* *Host tools in the cache keys.* The image actions use tools of the `ic-build`
  image (`podman`, `fakeroot`, libfaketime, `tar`, `sfdisk`, `veritysetup`,
  `jq`, ...) that aren't Bazel inputs. `ci/container/TAG` is an input of every
  image action and of the genrules that use these tools, so a new dev-container
  image doesn't serve images built with the old tools from the cache. `zstd`
  comes from `@zstd` everywhere (`build_disk_image.py` and `build_lvm_image.py`
  called the host's).
* *Release builds* (`--config=stamped`) build the partitions and images
  (`IcosVfatImage`, `IcosExt4Image`, `IcosDiskImage`, ...) without the remote
  cache, as before they were cacheable: PR builds write to that cache, and the
  stamped root and boot partitions embed the version, so nothing else could
  use them. The container filesystems and the binaries in the images come from
  the cache like all other release artifacts, as before.
* *Modes don't depend on the environment.* The image tools record the modes of
  the files they create, so:
  ** `tmpdir_wrapper.sh` and the genrules with their own scratch set
     `umask 022`, clear the setgid bit of their scratch directory (the sandbox
     directories on the `dind-large` runners are setgid, which made CI-built
     root partitions' root directory 2755) and drop a default ACL it would
     inherit. The ext4 image's root directory gets an explicit 0755.
  ** The container build context's files get 0755 or 0644 by their executable
     bit (`container_context.py`). `COPY` keeps the context's modes, and Bazel
     materializes inputs as 0555 locally but 0755/0644 when they come from a
     remote executor. SetupOS's `/commit-time` was the only copied file that no
     later step chmods; it is now `COPY --chmod=644` (it was 0555), which
     changes the SetupOS images.

Expected effect: on a PR that doesn't touch `ic-os/components` or the
component binaries, `rootfs-tree.tar` comes from the remote cache and podman
never runs. A PR that doesn't change any binary baked into an image gets every
partition and image from the cache. A PR that does change one rebuilds only the affected
`partition-root` → verity → disk/upgrade chain, and on RBE that chain runs on
remote workers instead of the CI driver.

Cache size: every CI job uploads its results
(`--remote_upload_local_results=true`), so the newly cached partitions and
compressed images are uploaded for each of the ~20 image envs. On stamped
release builds the commit hash is baked into the root and boot partitions, so
those upload on every merge and rarely hit. #3256 measured 24G vs 6.9G per
build. The growth must be measured on CI (`ci-rbe-evaluation` and
bazel-remote).

Scratch space: a root partition build extracts about 3 GB and creates a
10 GB sparse image, and `create_test_img` unpacks a whole SetupOS disk image.
The RBE workers only have a 1 GB `/tmp` (#10797, and the `no-remote-exec` on
`guest-img` in `bazel/mainnet-icos-images.bzl`), so `tmpdir_wrapper.sh` and the
genrules that unpack images (`create_test_img`, `extract_boot_partition_files`)
create their scratch directory in the action's working directory instead of
`/tmp`: the execroot on the worker's disk remotely, the sandbox directory under
the output base locally. Check the disk headroom of the `ci-main.yml` runners
and of the RBE workers.

== `build-ic` on PRs

`build-ic` is the uncached side of the `build-determinism` comparison, and it
built every IC-OS image on every PR. On PRs it now builds the images
(`build-ic.sh -i`) only if:

* the PR changes an input of an image that `build-ic.sh -i` builds, as
  reported by `ci/scripts/targets.py build --include_manual` (the bundle
  targets are tagged `manual`), or
* it changes `ci/container/build-ic.sh` or `ci/scripts/targets.py`, which
  aren't Bazel inputs, or
* it deletes a file: a deleted file (e.g. one a glob picked up) isn't in the
  head's Bazel graph, so the query can't see what depended on it.

The cached images of the other PRs were checked against an uncached build
when their inputs last changed. `master`, `rc--*`, scheduled and all-targets
runs still always build them.

== Supported build environments

[cols="1,2,2,2"]
|===
|Environment |How Bazel runs |Container steps (`IcosContainer*`, bootloader, fuse2fs) |All other image steps

|DFINITY CI (`dind-large` runners, `ci-main.yml`)
|In the `ic-build` container (`--privileged`, tmpfs at `/tmp/containers`),
with the `bazel-remote` cache from `bazel/conf/.bazelrc.internal`. PR jobs
upload results.
|Locally on the runner, as before
|Sandboxed (`linux-sandbox`) on the runner; results cached in `bazel-remote`

|Namespace (`ci-rbe-evaluation.yml`, `.github/actions/bazel-namespace`)
|`--noworkspace_rc` with `.bazelrc.build`, the `nsc` endpoints and

|Locally on the RBE driver, as before; scratch on `/namespace/scratch` via `TMPDIR`
|Remotely on the RBE workers, which run the same `ic-build` image

|Local (`ci/container/container-run.sh`, podman or Docker, or the VS Code

|In the `ic-build` container: privileged podman, or Docker with
`SYS_ADMIN`/`/dev/fuse` and unconfined seccomp/AppArmor. Reads the
`bazel-remote` cache on the DFINITY network; use `--config=local` without it.
|Locally in the container, as before
|Sandboxed (`linux-sandbox`) in the container
|===

Notes:

* `fakeroot` and Bazel's sandbox: `linux-sandbox` runs each action in a user
  namespace where only the caller's uid is mapped. `fakeroot` tries the real
  `chown` first and only ignores `EPERM`, but in that namespace a `chown` to an
  unmapped uid fails with `EINVAL`. `tmpdir_wrapper.sh` therefore sets
  `FAKEROOTDONTTRYCHOWN=1`, so ownership lives only in fakeroot's state file,
  as it always effectively did for a non-root build.
* `faketime` and Bazel's sandbox: the `faketime` wrapper (even with
  `--disable-shm`) and libfaketime itself create a POSIX semaphore and shared
  memory in `/dev/shm` named after the PID, to share a running clock between
  processes. Sandboxed actions each get their own PID namespace but share
  `/dev/shm`, so concurrent actions collide (`sem_open: File exists`,
  `shm_open failed: File exists`). The image tools therefore preload
  `libfaketime` directly with `FAKETIME=1970-1-1 0:0:0` and
  `FAKETIME_DISABLE_SHM=1` (`faketime_env()` in
  `toolchains/sysimage/utils.py`, `debugfs_with_frozen_clock()` in
  `partition_tools`). A frozen absolute time doesn't need the shared clock.
* The image targets only require Linux (`target_compatible_with =
  @platforms//os:linux`), but they are x86_64 images and their tools expect
  the x86_64 Debian layout, e.g. `/usr/sbin/debugfs`. On macOS they are
  skipped, as before. Build them in the dev container on an x86_64 Linux host.
  libfaketime is looked up in the usual Debian/Ubuntu, Fedora and Arch
  locations, or at `$LIBFAKETIME` when that is set (for running the tools, e.g.
  `setupos-disable-checks`, outside Bazel). If it is missing, the image tools
  fail instead of silently producing non-reproducible images.
* On a bare Linux host (no dev container) the image steps need the same host
  tools as the `ic-build` image (`podman`, `fakeroot`, `libfaketime`,
  `cryptsetup-bin`, `fdisk`, `zstd`, `jq`). If `linux-sandbox` can't create
  namespaces there (e.g. Ubuntu's `apparmor_restrict_unprivileged_userns`),
  Bazel uses its process-wrapper sandbox instead. Rootless podman needs the
  same namespaces, so such a host couldn't build images before either.
* *Escape hatch:* `--config=icos_host` restores the old behaviour in any of the
  three environments: every `ic-os` image action runs on the host,
  unsandboxed. Use it if the image steps fail sandboxed or on the Namespace
  workers, e.g. because `fakeroot` (SysV IPC, `LD_PRELOAD`) doesn't work under
  the worker isolation. If only SysV IPC is the problem, a narrower fix is
  fakeroot's TCP daemon (`fakeroot --faked faked-tcp`, shipped in the same
  package), which doesn't use SysV message queues. On Namespace it can be
  appended to the Bazel arguments of `ci-rbe-evaluation.yml`.

== Not decided here: the executor of the container step

The only steps that still need the host are the container builds
(`IcosContainerBuild`, `IcosContainerBaseImage`, the bootloader tree), which
run rootless `podman build`: their Dockerfile `RUN` steps
(`update-initramfs`, `adduser`/`addgroup`, `systemctl enable`, the SELinux
policy build in `prep.sh`) execute the target's own binaries as root inside
the target filesystem. Rootless podman needs unprivileged user namespaces plus
the setuid `newuidmap`/`newgidmap` helpers, which neither Bazel's
linux-sandbox nor the RBE workers provide. So these actions run on the host
(on RBE: on the driver), and the CI containers that run them stay
`--privileged` with a tmpfs at `/tmp/containers`.

Their outputs are cached, so this only costs anything when a container
filesystem's inputs change. Replacing podman, so that these steps also run
sandboxed and remotely and the CI containers can drop `--privileged`, is a
separate decision. The candidates (a KVM microVM, which #11784 prototyped and
which `/dev/kvm` on the `dind-large` runners and the Namespace RBE workers
would support, or an execution-free assembly of the filesystems) are for the
IC-OS team to weigh.
